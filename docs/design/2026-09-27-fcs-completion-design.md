# IronNestFCS 收尾设计：可靠执行、反炮兵调度与玩家指挥

日期：2026-09-27。讨论范围：本轮项目收尾讨论。

状态：设计规格，尚未完成实机验收。2026-10-04 按玩家澄清修订停止与保留弹语义；本节修订优先于旧文中“暂停旧任务后续跑”的描述。

代码核对基准：当前工作区，HEAD 为 `af995c49`；工作区中的射表改动与回归检查也作为现状记录，不视为已经发布的 Baseline。

本文确定最终版本要解决什么问题、玩家可以下达什么命令，以及系统必须怎样回应。三维控制台的造型、布局、材质和具体控件后续再设计。本文中的命令是交互语义，不代表现在就要做同名实体按钮。

文中区分三类依据：**当前代码事实**、**历史记录或本轮玩家反馈**、**本次设计决定**。历史实测不自动代表当前游戏版本仍完全相同；有冲突的机制单独列入验证清单。为使逻辑能够落地，本文补齐了讨论中未逐项指定的默认行为，不把这些默认值冒称为此前逐项确认过的结论。

## 1. 最终版本想要什么

FCS 保留“下令以后，看铁巢自动把炮打出去”的爽快感。玩家可以继续开启全自动扫荡，也可以亲自决定打谁、用什么射击方案、先做哪一项。系统负责复杂计算、机械操作和双炮协调。

这轮工作的完成条件只有三个方向：

| 方向 | 要解决的问题 | 完成后的体验 |
|---|---|---|
| 取消、接管与膛内状态 | 停止不可靠，半装填、装药、合栓和武装状态容易与任务脱节 | 玩家能暂停、取消、重新接管；旧任务不会继续操作，新任务知道炮里有什么 |
| 反炮兵调度 | 不会可靠利用倒计时暂停；落地次序、紧急移动和旧坐标会破坏计划 | 系统按实际倒计时状态组织射击，移动以后重新解算并恢复，保留 Baseline 可选 |
| 玩家指挥与控制台 | 小键盘入口不直观；玩家的打击意图不能完整表达，也容易被扫荡覆盖 | 玩家选对象、选方案、安排顺序；地图呈现有时间含义的标绘，控制台呈现整项计划 |

实施顺序为：**执行可靠性 → 反炮兵逻辑 → 三维控制台整合**。第三方向的命令、状态和任务模型现在就确定，供前两步使用；外观实现放在最后。

这轮不承担机器学习、通用关卡规划器、自动理解全部电报、完整改造座舱，或彻底移除全知数据源。行进间射击保留为候选增强，不加入本轮完成门槛。

## 2. 为什么现在的自动化还不能表达玩家的意思

### 2.1 玩家要的结果常常比“击毁一个实体”更具体

本轮讨论明确了玩家最想参与的是**决定打谁**。进一步看，决定打谁还包含对这次打击的要求：整列覆盖、指定弹种顺序、双炮齐射、首发、暂缓其他攻击。

三个关卡场景构成本设计的主要依据。

**拦截列车。** 系统已经能估计列车运动、识别附近同向同速成员，并计算覆盖落点。但自动扫荡可能先打附近目标，提前破坏车站或铁路，使列车停车。玩家想看的“第一发 HE 命中移动中的整列火车”因此消失。完成通关与完成玩家想要的这次射击，是两个不同的验收结果。

列车的情报又往往通过位置、时间和速度表达。玩家没有一个天然可点击的实时列车图标，也无法像程序一样持续驱动瞄准。这需要系统把情报与计算整理成可选择的目标和方案。

**支援友军。** 中途电报可能要求先向某目标发射催泪弹，再发射杀伤弹。玩家读电报、判断目标时，全知扫荡可能已经发出杀伤弹。之后再调整优先级，无法撤回已经出膛的炮弹。系统也不能用“已经击毁目标”替代“按指定顺序完成支援”。

**与敌方铁巢对射。** 按玩家描述，该目标需要四发 AP，受击后会紧急转移。玩家希望集中双炮，以两轮齐射完成攻击。现有逐个目标调度可能先清理观测员，再零散打主目标，期间复用旧坐标造成落空。两轮齐射能否稳定达到预期，还要验证受击转移触发时机、两发实际落地间隔和毁伤规则。

这些需求可以由有限的任务模板表达，不要求系统自行理解整场战役。

### 2.2 当前 Baseline 的能力与边界

当前代码的自动流程是扫描、排序、向空闲炮管派发单发任务、完成后再扫描。排序先看目标优先级，同级再比较距离和炮塔转角构成的时间成本。因此玩家感受到的“近目标先打”有代码依据，但排序并非只有距离这一项。

当前 `FcsModule.PickTarget()` 排除 FDC、装甲和地下目标；自动路径创建单点任务，软目标主要使用 DRIL。聚群与移动集群代码仍保留在仓库中，但没有接回当前 Baseline 自动派发路径。README 和部分旧文档描述的是其他时期的功能组合，不能把它们全部当成当前默认行为。

现有 `ArtilleryTask` 主要承载一发炮弹的执行信息。它不足以单独表达“同一目标先 TEAR 后 HE”“两轮双炮齐射”“整个编组必须被覆盖”。需要在单发任务之上保留一项玩家计划，并让它拥有阶段、约束和结果。

代码依据：[FcsModule](../../IronNestFCS.Logic/FcsModule.cs)、[TacticalDecider](../../IronNestFCS.Logic/FCS/TacticalDecider.cs)、[ArtilleryTask](../../IronNestFCS.Logic/FCS/ArtilleryTask.cs)、[FSC](../../IronNestFCS.Logic/FSC.cs)。

### 2.3 原作的机械感与等待感需要保留

铁巢的操作体验包含接收情报、测绘、准备弹药、驱动笨重机构、击发和等待结果。FCS 可以接手大量重复操作，但玩家仍需要看懂命令如何变成一次射击。

地图因此采用“标绘”的信息组织方式：标记某时刻的已知位置、行进方向和预计拦截点。后台可以精确计算，前台按情报和计划事件更新。默认不以移动图标、逐秒落点倒计时和连续弹道动画构成现代作战大屏。

这也让玩家保有一次下令后的期待：知道系统打算怎样打，看见机构执行，听见炮响，再等待结果。

## 3. 游戏机制与工程约束

### 3.1 两管炮共享方位和全局扳机

两管炮共用一个炮塔方位，各自有独立仰角和装填机构。装填可以并行，指向不同方位的击发需要协调共享炮塔。全局扳机会击发所有已武装炮管，因此“取消了左炮的软件任务”并不等于“右炮开火时左炮不会响”。

武装状态、方位控制权和击发许可必须共同核对。只有明确组成同一次齐射的炮管才允许共同处于自动击发集合中。方位偶然接近不能自动赋予齐射权限。

这是取消处理、双炮齐射和不同落地时序的共同基础。依据：[CLAUDE.md](../../CLAUDE.md)、[TriggerConsole](../../IronNestFCS.Logic/FCS/TriggerConsole.cs)。

### 3.2 一发炮弹具有多个不可混淆的阶段

典型过程为选弹、推弹头、选取并装入发射药、机构合栓与准备、瞄准、武装、击发、飞行、命中或落空、退膛回位。实际顺序和可逆操作须按游戏机构验证。

以下状态不等价：有弹头、选中了装药档、发射药已经入膛、炮闩已经合上、机构允许发射、击发装置已武装、扳机请求已提交、炮弹实际出膛。

炮弹飞行与退膛、下一轮装填可以重叠。炮管空闲以后，上一发仍可能在飞；上一项计划取消以后，已经出膛的炮弹仍会产生效果。

### 3.3 移动目标复用解析外推

按玩家观察，游戏中的单位移动几乎都是匀速直线运动。现有实现以位置样本估速，冻结 `AimP0`、`AimVel`、`AimStartTime`，再用下式计算提前点：

```text
预计命中位置 = 快照位置 + 速度 ×（距快照的时间 + 预计飞行时间）
```

当前瞄准循环仍会逐帧代入公式、换算方位仰角并驱动机构。运动模型在冷启动或显著变速时更新；停车检查在装填和瞄准期间都会使用最近一次雷达扫描的缓存，并非每帧重新读取全部实体、估计整条运动轨迹。缓存的采样时间必须保留，不能把缓存查询误当成一次新观测。

保留这条路径。目标停车、重新启动、转向、速度明显变化或坐标基准改变时，重新验证快照。速度尚未建立属于未知，不应作为零速度使用。现有代码对停车后的再次启动需要补足验证。

同向同速且相对位置不变的列车编组，可以复用成员相对位置和覆盖圆。整体平移不改变覆盖圆半径，无需每帧重新寻找最佳子集。

当前 `ToFTable` 工作区版本采用固定装药下飞行时间随距离近似线性的实测模型。它仍是估计，不能直接代表实际落地事件，也不保证所有弹种和距离上的误差相同。公式外推与飞行时间估计的适用范围须通过当前游戏版本验证。

依据：[TargetLeadSolver](../../IronNestFCS.Logic/FCS/TargetLeadSolver.cs)、[TacticalRadar](../../IronNestFCS.Logic/TacticalRadar.cs)、[ToFTable](../../IronNestFCS.Logic/FCS/ToFTable.cs)、[移动目标历史设计](../moving-target-tracking.md)。

### 3.4 反炮兵机制：历史证据与待验证部分

历史 CBT 方案在提交 `b0a1754` 的 `docs/cbt-mode.md` 和 `CbtMonitor.cs` 中保存。以下数值用来说明机制和历史取舍，不直接变成新版本的固定常数。

| 机制 | 依据与置信范围 | 对设计的影响 |
|---|---|---|
| 初始倒计时约 600 游戏秒，第一发落地启动 | 历史文档记录，需当前版复测 | 开局准备和首个落地时刻影响可利用时间 |
| 击杀火炮增加约 30 秒、5 点征用点 | 历史记录称有 14 个样本 | 清理火炮同时带来时间和经济收益 |
| 倒计时可超过初始值 | 历史样本出现 656.6 秒 | 不能把 600 当上限，也不能仅凭剩余值判断是否启动过 |
| 击毁 FDC 能暂停倒计时 | 历史记录及玩家反馈 | FDC 是可利用的暂停资源，不能简单按最高威胁立刻打完 |
| 后续我方炮弹落地可能解除暂停 | 历史落地顺序失败记录 | FDC 前后的在飞炮弹和后续发射都要参与协调 |
| 移动暂停以后按原值继续，不恢复到 600 | 历史样本为约 232.8 暂停、232.5 恢复 | 移动购买的是准备时间，不是重置剩余生命 |
| 移动价格历史值为 65 点 | 历史记录 | 移动后还需留下继续开炮的资源 |
| 暂停是否能无限维持 | 记录冲突：一处称直到我方落地，另一处记录停火约 278 游戏秒后恢复 | 不能写死无限暂停；状态机必须响应实际恢复事件 |
| FDC 仅出现于无尽反炮兵模式 | 历史版本的玩家识别经验 | 可作候选识别信号，不能冒充所有版本的通用保证 |

旧记录还把“45 秒移动冷却”与游戏效果写在同一张表内，而代码中它是防重复采购的策略限制。新实现必须把游戏规则、探针观测、策略参数分开。

CBT 应读专用 `CounterBatteryTimer` 的运行、过期和剩余时间。历史探查指出 `FireMission.RunningTimers` 存在其他通用计时器，不能仅因它叫计时器就替代 CBT 时钟。

### 3.5 主线程、时钟与热重载

游戏对象访问继续位于 Unity 主线程；沿用现有宿主、契约、Logic 热重载边界。此次不引入跨线程操作 IL2CPP，也不在可重载 Logic 中新增需要重复注册的 IL2CPP 类型。

运动、射表和 CBT 顺序使用同一游戏时间轴；UI 动画、诊断和真实时间超时单独命名。游戏暂停和时间倍率变化要显式处理。旧文档中的 `timeScale=4` 是某次运行条件，不是常量。

所有任务所属的子协程、延迟点击、后台转向和装饰计算器动作均须能够登记、失效和清理。不能仅依据“外层有 finally”就认定所有嵌套动作已停止；停止、异常和热重载的真实清理路径必须验证。

## 4. 共同设计：玩家计划、单发执行与物理状态

### 4.1 计划必须独立于单发任务存在

增加一个有限的计划层，概念上称为 `FirePlan`。名字可以在实现时调整，但必须保存以下语义：

| 信息 | 用途 |
|---|---|
| 计划身份和修订号 | 防止旧回调、旧任务修改已取消或已改派的计划 |
| 来源 | 玩家命令或自动策略，决定谁有权修改和撤销 |
| 目标引用 | 单个实体、固定编组或明确的位置目标，不能只存一个屏幕点击坐标 |
| 射击方案 | 单发、整组覆盖、弹种顺序、两轮双炮齐射 |
| 硬性要求 | 指定弹种、成员集合、单发上限、移动中命中、首发、顺序条件等 |
| 执行阶段 | 准备、等待条件、发射、等待结果以及下一阶段 |
| 调度要求 | 普通排队、优先排队、专注执行 |
| 授权与暂停原因 | 谁下令、是否允许执行、为什么等待 |
| 结果和在飞记录 | 实际完成了哪些发、还剩什么、哪些结果尚未知 |

`ArtilleryTask` 可以继续承担一发的执行；每一发必须指向所属计划、阶段和炮位占用身份。自动策略也提交同样的计划，不能绕过执行器直接开炮或清洗炮管。

### 4.2 四种状态分别记录

| 状态对象 | 回答的问题 |
|---|---|
| 玩家计划 | 还要做什么，是否被暂停或取消？ |
| 炮管与装填机构 | 炮里有什么，机构在哪一步，是否仍在运动？ |
| 资源占用和执行权限 | 谁能驱动炮塔、采购台、武装和全局扳机？ |
| 已发射炮弹 | 哪发真实出膛，预计何时落地，结果是否已确认？ |

“取消计划”可以立即撤销后续授权，机构随后进入交接过程。在机构状态尚未确认时，不能把炮位宣布为空闲。计划终止也不能清除已经发射的炮弹记录。

### 4.3 授权顺序

执行任何自动击发前，都要依次满足：场景和对象有效；执行未被玩家暂缓；炮管状态已确认；命令和资源仍归当前计划；弹种、装药和解算符合要求；计划前置条件成立；本次武装集合与预定击发集合一致。

玩家取消、暂缓和模式切换会使旧许可失效。CBT 压力、超时、缺弹和目标高优先级不能恢复这些许可。

普通优先级只在满足约束的候选计划之间比较。明确的弹种顺序、齐射条件和整组覆盖要求不能被优先级数字冲掉。

## 5. 方向一：取消、接管与膛内状态

### 5.1 当前痛点及其原因

当前切手动时，`CancelOrForceFire` 对进入装填阶段的自动任务设置 `forceFire`，以“打完这发”避免中途卡膛。这解释了旧行为的来由，但与玩家希望撤销射击的意思不一致。

`AssessChamber` 把大量“有弹但不能开火”的情况归为 `ShellLoaded`。选药、药已入膛、合栓和机构运动没有被充分区分。`ChamberCharges()` 读取选药控制器的字段，它在半装填、撤销和重载时是否仍代表实际入膛数量，需要验证。库存包数更不能作为膛内装药量。

看门狗目前可能释放任务槽位和锁后立刻重新派发，而旧任务的收尾代码仍会清空对应炮位。静态路径存在旧任务影响新任务的风险。`WaitFire` 与退膛等待的部分超时路径还会继续返回，调用方可能把“等不到确认”当成“已经成功”。这些是代码审查发现，不能冒称本轮已经实机复现。

### 5.2 操作语义

本次设计采用“撤销后续射击授权，尽量保留膛内弹药；退弹是独立操作”的默认规则。

| 操作 | 对计划的影响 | 对炮管的影响 | 后续如何继续 |
|---|---|---|---|
| STOP／切回手动 | 撤销所有现有待执行任务，包括手动来源；不保存续跑队列 | 停止追加机构动作，解除武装，保留弹药；已提交击发只观察结果 | 明确切回 AUTO 后读取现场，重新选目标和解算；新手动命令也是新授权 |
| 取消计划 | 终止该计划所有尚未不可逆的阶段 | 解除该计划武装和控制权，保留可保留的弹药 | 新建计划或手动接管，不复活原计划 |
| 退弹复位 | 暂缓涉及该炮管的阶段 | 执行可验证的退弹和机构复位流程 | 确认空膛及机构可用后，重新评估计划 |
| 改派目标／方案 | 旧的未执行部分失效，产生新修订或新计划 | 先完成交接，再按实物状态判断能否复用 | 重新解算、重新检查前置条件 |
| 再次开启 AUTO | 从当前目标和实物创建新任务，旧任务不复活 | 优先利用已有整发，空管正常装填 | 无合适目标的保留弹等待下一轮扫描 |

产品上不保留含糊的“停止”同时代表清队列、强发、退弹三种行为。文案和按钮可以以后设计，但这些语义不得混用。

### 5.3 按实物状态处理取消和恢复

| 实际状态 | 收到暂停或取消后的处理 | 新任务的接管条件 |
|---|---|---|
| 空膛、机构静止 | 撤销待办，解除占用 | 确认可装填后接任务 |
| 弹头正在转运或推入 | 禁止继续追加动作，等待当前机械过程到可交接位置 | 重新读取弹种、位置和机构状态 |
| 弹头已入膛，尚未装药 | 保留弹头 | 弹种符合才进入装药；不符合则换炮或要求退弹 |
| 选药完成或发射药正在推入 | 不依据选择档位宣称药已入膛，不重复执行推药 | 确认实际装药和机构进度 |
| 弹与药已就位，尚未完成准备 | 保留，停止新增步骤 | 从已确认的实际阶段继续 |
| 已合栓但未武装 | 保留整发；合栓状态与武装状态分开记录 | 弹种、实际装药、射程和机构许可均通过 |
| 已武装、尚未提交不可撤销的击发 | 执行实际解除武装并回读 | 证明不会被另一管的全局扳机带响 |
| 扳机请求已提交，是否出膛尚未确认 | 记录“击发待确认”；禁止把它当可任意复用的整发 | 等待发射或拒绝的确切结果，避免重复击发 |
| 已出膛、正在退膛 | 保留在飞记录，完成退膛交接 | 实际回位完成以后接下一发 |
| 读数未知、互相矛盾或对象失效 | 进入恢复／需要处理状态，停止该炮管自动击发 | 明确恢复成功，或玩家处理后重新检查 |

“已武装后取消”必须覆盖另一管随后开火的情况。仓库归档的接口桩存在解除武装方法，但仍需验证场景绑定、臂杆动画和继电器状态；不能只修改一个软件布尔值。

### 5.4 膛内弹药的复用规则

复用依据为实际弹种、已确认的实际装药、可达射程、解算有效范围和机构状态。用户明确要求 HE 或 AP 时，不能沿旧回退链悄悄换成其他弹种。

对暂停或取消后留下的弹药，记录其保留原因。匹配的新计划可以复用；不匹配时优先使用另一管，或明确等待退弹处理，不能为了让队列继续而暗中丢掉保留弹。用户主动下达退弹操作时，界面应说明它可能损失现有装填。

2026-10-04 玩家明确纠正：游戏采用简单弹道，不以历史“高装药近距打偏”记录设置复用禁区。实际装药多于最低需求时照常复用，仰角与飞行时间均按实际装药解算。AP＋6 包装药可用于原本推荐 DRIL 的近处软目标；自动推荐不是强制弹种约束，仍须遵守目标免疫、可达射程和友军范围检查。用户手动明确指定弹种时仍严格匹配。

膛内状态记录应当包含未知值。读取失败不能记作空膛、零装药或已经解除武装。

### 5.5 槽位、锁和子动作的所有权

每次炮位占用带有身份或代次。释放槽位、释放锁、完成回调和恢复回调都要检查自己仍是当前持有者。旧任务的 finally 只能清理自己的资源，不能按“左炮／右炮”直接抹掉新任务。

取消过程依次完成：撤销授权、使旧命令失效、收回武装和机构操作、停止或收束所属子动作、核对实物、释放可释放的资源、发布交接结果。允许幂等重复调用，禁止重复退弹、重复采购或重复派发。

子动作包括装填、采购、确认开关、延迟点击、后台炮塔预约以及装饰计算器同步。看门狗只能请求进入这条恢复路径；超时本身不能证明成功，也不能无条件强制复位共享锁后让新任务进入。

当无法证明解除武装成功时，由于全局扳机可能带响该管，需要暂缓全局自动击发。纯装填故障在共享资源和武装状态均已确认隔离时，可以仅隔离一管，让另一管继续。

### 5.6 目标保留、取消排除与热重载

STOP 释放未提交射击的旧目标占用，重新 AUTO 时按当前情况选择；已提交、已出膛或结果未知的记录继续占用观察窗口。玩家明确取消某项目标计划时，释放计划占用，但为其目标或固定编组建立本局自动排除，直到玩家明确恢复自动选择；玩家重新提交同目标计划属于新的明确授权。策略撤回过期候选、模式切换清理自动候选，不自动产生这种本局排除。

排除使用场景和目标实例身份。无尽模式复用字符串 ID 时，新生成单位不能无条件继承旧单位的取消记录；无法区分实例时，显示该不确定性并采用明确的重置规则。

热重载停止旧逻辑的全部动作，新逻辑默认暂缓，重新绑定并读取实物，不能自动重放旧队列。已出膛记录需要以不携带 IL2CPP 引用的值数据交接，或通过可验证的游戏观测重建；若两者暂未实现，必须进入“可能存在未确认在飞炮弹”的状态，禁止承诺首发、严格落地顺序和立即恢复扫荡。不能按固定等待秒数假定现场已经清空。

### 5.7 玩家直接操作原作机构

玩家改变炮管装填、武装或共享炮塔时，系统撤销受影响的旧执行许可，暂缓相关自动动作，重新读取实物。不能把手动改动立即纠正回去，形成玩家与脚本争抢开关的情况。玩家再次授权后按现场建立新任务，兼容的膛内弹药可以复用；不兼容的部分明确说明，不续跑旧机构进度。

玩家手动武装了不属于本次齐射的另一管时，自动全局击发必须等待交接，不能顺手把它打出去。无法观测某类手动动作时，要在发射前通过实际状态核对挡住冲突，并将观测缺口列入实测，不能宣称已覆盖所有手动行为。

## 6. 方向二：让反炮兵模式利用机制，并且可靠地恢复

### 6.1 为什么需要按落地和效果调度

反炮兵模式的关键资源包括剩余时间、炮弹与装药、征用点、炮管准备程度，以及仍可用于暂停倒计时的 FDC。把 FDC 当作普通目标尽早击毁，可能恰好浪费暂停；一发更早发射、飞得更久的炮弹在它之后落地，就可能让倒计时立即恢复。

因此不能沿用“先入队、先装填、先发射，就会先落地”的假设。单发炮弹的装填和飞行可以重叠，不同距离、装药与弹种的飞行时间也不同。双炮提高吞吐量的同时，增加了必须协调的在飞事件。

当前代码保留了部分 `FreezeWindow`、FDC 延迟和双炮等待路径，但 Baseline 并没有启用完整 CBT 策略。旧路径可以提供经验，不能直接恢复全部开关就视为问题已解决。

### 6.2 CBT 状态与移动状态分别表示

倒计时观测至少区分以下情况：

| 状态 | 判据与行为 |
|---|---|
| 尚未确认 | 读数、场景识别或引用不可靠；停止依赖精确 CBT 时序的自动承诺，显示原因 |
| 开局尚未启动 | 由有效的计时器状态与历史事件确认；允许准备，规划首个落地 |
| 正在运行 | 读取实际剩余值与运行状态，持续修订可执行计划 |
| 已暂停 | 记录已知原因或原因未知；利用准备时间，并监测真实恢复 |
| 已到期／场景结束 | 撤销本场景自动动作，按实际游戏结果收束 |

移动另有“请求、已接受、正在移动、重新定位、恢复完成／失败”的生命周期。不要把移动、FDC 暂停、玩家暂缓和游戏暂停挤进同一个布尔值。观察到剩余时间没有变化，也不能直接断言 FDC 生效：游戏暂停、时间倍率、对象读取失败都会产生类似表象。

历史上出现过停火期间自行恢复的记录。所以进入暂停状态以后仍需读取计时器；不能等自己认定的“下一发落地”才允许改变状态。

### 6.3 在飞记录独立存在

每次实际出膛创建一条发射记录，至少包含：所属计划和阶段、炮管、弹种、实际装药、真实发射时刻、当时的本舰位置、目标及瞄准快照、预计落地时间范围、观测到的实际结果。

以下事件严格分开：

1. 已获准击发。
2. 已发送扳机操作。
3. 已确认炮弹出膛。
4. 预计已到落地时间。
5. 已确认落地、效果或目标状态改变。

当前 `InFlight` 会依据预计时间移除记录，这不够支撑严格的效果顺序。新记录到达预计时间后先变为“等待结果确认”；依据可用事件更新结果。目标消失也要区分击毁、离开任务范围和场景卸载。

实际发射事件优先于软件意图。玩家手动打出去的炮弹也会影响 CBT，能观测时应加入记录；无法完整观测时标记存在未知在飞事件，取消严格落地顺序的承诺。归档接口中的出膛事件和预测字段可作为验证入口，不能仅凭接口名字认定已经能可靠订阅。

预计落地使用误差范围，误差需按现有射表与实测校准。没有证据时不能编一个极小误差来宣称顺序有保证。记录过期、重载或丢失结果，应结束为“未确认”，而不是补写命中。

### 6.4 FDC 应位于这一批攻击的最后一个落地事件

当策略决定使用 FDC 暂停窗口时，建立一个明确的阶段边界：先前已经发射的非 FDC 炮弹需要先完成可能唤醒倒计时的效果，再让 FDC 打击产生暂停效果。

这个边界还要登记本批次中尚未发射、但已承诺排在 FDC 之前的射击。它们实际发射以后，才有可靠的发射时刻用于更新落地范围；不能因为眼下在飞列表为空，就忽略另一管正在准备的那一发。其他未承诺的候选暂不派发。

以已验证的飞行误差为前提，调度约束为：

```text
FDC 预计最早落地时间 > 先前相关炮弹预计最晚落地时间的最大值 + 保护余量
```

这是选择发射时机的条件，不是判断 FDC 已经击毁的条件。具体还要考虑瞄准、装填、武装和当前平台运动导致的解算变化。等待期间持续修订预计时间，发射前再核对；无法满足时就撤回该承诺，重新排程。

一旦提交这个阶段边界，自动策略不再插入会破坏暂停收益的新射击。玩家若另下开火命令，应得到“这会使暂停提前结束／顺序无法保证”的直接反馈，并明确改变计划；不能表面接受两个互相冲突的要求。

FDC 发射以后等待实际效果或计时器状态确认。若未暂停，按仍在运行的 CBT 处理；若已暂停又被迟到炮弹或未知事件唤醒，立即按最新剩余时间重算，不困在“应当暂停”的软件状态里。

等待一个尚未发射的长飞行时间炮弹先执行时，FDC 任务不能占住对方必需的共享炮塔。等待者保留计划和可保留的装填，释放尚不需要的共享资源；重新取得控制权后再检查武装和解算。当前部分延迟路径持有炮塔，必须特别审查这种相互等待。

### 6.5 暂停期间准备下一轮

暂停的价值在于把装填、采购、转向和计划选择移到不消耗 CBT 的阶段。新策略优先形成可执行的下一轮，再主动发射恢复战斗。

同一目标、同一方位且明确绑定为齐射的双炮，可以共同准备并通过一次全局扳机击发。不同方位的两发仍需先后取得炮塔。希望落地接近时，要把转向、稳定、武装确认和飞行时间差一起纳入可行性判断；机械上来不及就报告达不到要求。

准备完成并不意味着允许开火。发射还要满足玩家授权、弹种顺序、编组覆盖及其他阶段门槛。若玩家在暂停窗口下达暂缓，CBT 策略不得以“窗口将结束”为理由强发。

暂停自行结束、FDC 已被其他行为击毁、资源不足或目标移动导致方案失效时，重新评估当前情况。允许策略降级为普通 CBT 生存调度，但不能悄悄更改玩家计划的硬性要求。

### 6.6 紧急移动是一项统一的恢复事务

移动会同时影响炮塔解算、目标相对坐标、炮位任务和倒计时。它必须由同一条流程管理，不能由“采购动作”“坐标刷新”“炮管清理”各自猜测其他部分已经完成。

| 阶段 | 必须完成的工作 |
|---|---|
| 接受移动请求或检测到手动移动 | 暂缓新派发与自动击发，提升位置代次，使旧解算和旧击发许可失效 |
| 收回正在执行的命令 | 通过第五节的交接流程处理两管武装、机构和共享资源；保留上层计划及已发射记录 |
| 发出移动操作 | 自动移动须先有玩家启用 CBT 自动移动的授权；核对资源，保证同一请求不重复采购 |
| 确认移动已发生 | 依据实际位置、移动状态或可靠事件确认，不能把“点击了采购”当作“已经开始移动” |
| 等待移动稳定 | 保持自动击发禁止；位置样本和场景引用有效，并满足经实测确定的稳定条件 |
| 重建解算 | 重新获取本舰位置与目标运动状态，重算距离、方位、仰角、装药可行性和飞行时间 |
| 核对机构并交还计划 | 保留兼容弹药，隔离未知状态；满足当前授权后重新派发尚未完成的阶段 |

玩家手动移动与自动购买移动进入同一条恢复流程；在指挥模式中也要检测。不能只在自动扫荡的低频扫描内检查，然后让炮在两次扫描之间使用旧位置开火。发射前的位置有效性检查是最后一道必要检查。

移动期间再次收到请求应合并或明确拒绝重复请求。一次采购超时但结果未知时先查实际状态，不能盲目再买。进入计时器暂停也不是再次采购移动的依据。

如果玩家在移动期间暂停、取消计划或切换模式，移动结束只能恢复实物和可用性，不能恢复已经撤回的执行授权。

本轮先保证移动中暂缓自动击发、移动后恢复正确。紧急移动方向随机，并不否定匀速模型，但行进间射击还涉及炮口运动、地图基准和弹道实现是否继承本舰速度等问题，后续单独验证，不顺带加入本轮。

### 6.7 坐标必须有唯一含义

约定新计划层与运动模型使用统一地图坐标，位置为公里，速度为公里／游戏秒。现有 `WorldPos`、`AimP0` 等字段仍涉及地图模型和 Unity 空间，迁移时必须显式转换，不能把已有向量直接当作公里。屏幕像素、地图面板局部坐标和世界坐标只在明确边界转换。若原作地图会以本舰重定位或旋转，先通过适配层恢复统一含义，不能假定现有字段天然就是固定地图坐标。

每份未发射解算绑定本舰位置代次。发射前必须满足：

```text
目标的预计命中位置 = 有效目标快照在命中时刻的外推位置
相对射击向量 = 目标的预计命中位置 - 本次有效发射位置
距离、方位、仰角、装药、飞行时间均由这份有效解算得出
```

本舰移动以后，即使目标方位几乎不变，距离也可能显著改变。当前静态复核路径存在仅在方位漂移超过阈值时才更新距离的情况，需要消除这种依赖。径向移动是必须单列的验收场景。

已经出膛的记录保留发射时快照，不能随着本舰移动重新改写原点。未出膛的计划则必须重算；不能只更新地图上的显示点，继续沿用原来的装药或飞行时间。

没有有效本舰位置、目标已脱离可信运动模型、地图对象重建中，都属于解算暂不可用。空引用不能转换为坐标零或视为移动结束。

### 6.8 时间与资源策略保持有限、可解释

CBT 策略比较的是：剩余时间是否足够等到下一次可靠收益、当前炮弹和征用点是否支撑这轮计划、是否应该保留一个 FDC、是否需要移动争取准备时间。

移动同样要考虑在飞炮弹是否会很快吃掉暂停收益。时间允许时，可以等待合适的事件边界再移动；已经临近生存期限时，按可验证的期限优先求生，不能为了追求一个完美暂停窗口一直等到到期。这个取舍只改变获准的自动策略，不越过玩家暂停，也不强发被取消的炮弹。

阈值和成本放入可校准参数，不把历史的 600、65、45 等数值散落在执行器里。自动移动作为 CBT 的独立选项，默认关闭；玩家开启后可由策略持续使用，不要求每次购买重复确认。关闭时显示相应的等待或失败原因。

支出要考虑移动后是否还买得起下一轮所需弹药。资源不够时报告缺口、等待可验证的收益或暂停计划。系统可以修改自己生成的普通扫荡方案；玩家指定的 AP、HE、TEAR 顺序和发数上限不得被经济回退覆盖。

这一步不需要通用搜索器或机器学习。先把少量明确规则做成能被观测、能恢复的状态转换，再用相同场景比较存活时间、征用点消耗与无效射击。

依据：[FSC](../../IronNestFCS.Logic/FSC.cs)、[MapTable](../../IronNestFCS.Logic/FCS/MapTable.cs)、[TargetRegistry](../../IronNestFCS.Logic/FCS/TargetRegistry.cs)，以及提交 `b0a1754` 中的 CBT 文档与实现。历史策略仅用于解释问题，不整体照搬。

## 7. 方向三：把玩家的打击意图变成完整命令

### 7.1 三个相互独立的选择

不能继续让一个“自动／手动”开关同时决定是否读取目标、是否生成任务、是否允许开火，以及是否启用 CBT。交互逻辑分成三个维度：

| 维度 | 选项及含义 |
|---|---|
| 指挥方式 | **指挥模式**：系统提供目标与方案，玩家提交计划；**自动扫荡**：系统在获准范围内自行生成计划 |
| 调度策略 | **Baseline**：普通调度；**CBT**：加入倒计时、FDC 与移动窗口的安排 |
| 执行开关 | **暂缓**：不再提交自动击发，处理交接；**运行**：执行已获授权且满足条件的计划 |

新启动和热重载默认进入指挥模式、Baseline、暂缓。玩家可明确选择自动扫荡与 CBT，然后启动；保留一次开启后持续自动开炮的体验。是否保存上次指挥方式可以以后作为偏好，但不能跨重载自动恢复开火许可。

提交计划代表授权其内容，执行开关代表当前是否允许系统行动。在暂缓时提交会入队等待；在运行时提交会按顺序执行，不要求每发再次确认。未提交的草稿永远不属于可执行队列。

切换指挥方式或调度策略时进入暂缓并完成交接，撤回尚未执行的自动候选，保留玩家计划与真实在飞记录。玩家明确继续后才执行新规则。切换不能清空本局手动排除或复活已取消计划。

指挥模式仍保留必要的目标读取和运动估计。它停止的是自动选择并授权新目标，不能像旧的“关闭自动”路径那样连所选目标的观测也一起停掉。

CBT 策略在指挥模式中可以调整已授权计划的准备和时机、提出 FDC 建议；不能自行增加未获授权的打击目标。自动扫荡下，它才可以自行选 FDC 和其他目标。自动移动是单独可见的策略选项，只有明确启用后才允许采购；两种指挥方式都遵守执行开关。

### 7.2 目标对象与屏幕标记分开

支持三种目标对象：

- **单个实体**：持续绑定同一目标实例，移动以后仍是它。
- **固定编组**：绑定玩家确认的一组成员，例如整列列车；保存成员身份和相对位置关系。
- **地图位置**：玩家明确要求向一个地点射击，不偷偷绑定附近单位；它不自动享有动态目标跟踪。

点选标记只改变当前选择，不产生射击任务。再次选择别的目标不会改写已提交计划，必须通过明确的改派操作。

编组可以由同向同速、空间关系和可用的游戏关联字段提出候选，再让玩家选择整组或单个成员。已确认的成员集合不因覆盖半径、预算、附近新出现单位而静默变化。若目标身份不可稳定识别，暂停这项承诺并说明原因，不能在相近坐标上自动换一个目标。

“整列”与“最大覆盖子集”分开。先确定要打的成员，再判断能否覆盖；不能先找一个 HE 能盖住的圆，再把圆里那几节称为整列。

### 7.3 从选择到执行的命令闭环

| 玩家操作 | 逻辑效果 | 必须反馈的信息 |
|---|---|---|
| 选择实体、编组或地点 | 创建／切换当前选择 | 选了谁、成员数、信息来源与标绘时刻 |
| 选择射击方案和弹种 | 编辑草稿，计算可行性 | 将发几发、按什么顺序、要求何时成立 |
| 查看方案 | 显示计划标绘与预计覆盖 | 全部覆盖还是部分覆盖，哪些条件还不满足 |
| 加入队列 | 固定计划修订并授权内容 | 排位、执行开关、首个等待原因 |
| 优先执行 | 提高尚未承诺的任务之间的次序 | 已出膛和已不可逆操作不能被撤回 |
| 专注执行 | 为这项计划建立独占的打击窗口 | 其他射击如何交接、是否已有在飞炮弹 |
| 暂缓／取消本次待发射击 | 保留计划进度，收回可撤销的击发许可 | 实际暂停到哪一步，膛内保留了什么 |
| 继续 | 重新验证目标、弹药、坐标与阶段条件 | 可继续，或仍然缺少什么条件 |
| 取消整项计划 | 终止未来阶段，保留已经发生的结果 | 尚在飞的炮弹、保留弹药、自动排除 |
| 退弹复位 | 对指定炮管执行独立的实物操作 | 可能损失的装填、过程和最终读数 |
| 重新标绘 | 根据当前可用观测更新一张有时间戳的标绘 | 此次采用的观测时间与计划状态 |

草稿预览只做读取与计算，不偷偷采购、推弹或占住炮塔。提交以后允许自动选择兼容炮管、在已验证范围内选择装药、更新提前量和准备时机。这些属于实现已授权方案。

更换弹种、减少编组成员、把一发改成多发、取消移动中命中要求、改变弹种先后或放弃齐射，都属于方案改变，需要玩家明确改派。单纯重新计算提前点不需要每次问玩家。

已出膛部分不能修改。改派只作用于未执行部分，并保留旧修订的发射和结果记录；不能把之前发生的射击事后改记到一个更容易成功的新目标上。

### 7.4 优先与专注各自解决什么

“优先”主要解决排队次序。它不许跳过当前不可逆动作，也不承诺其他目标完全停火。

“专注”用于列车首发、弹种顺序和集中攻击。接受后停止生成其他自动射击，暂缓其他计划尚可撤回的部分，收回两管的冲突武装与资源。实际交接完成才进入执行阶段；其他计划暂停期间仍保留其进度。

进入专注前检查所有已知在飞记录，并区分“首个发射”“首个落地”“目标仍在移动”这些不同条件。开局首发承诺要求本次场景的发射记录足以证明尚未发射；不能把未知历史或热重载后缺失记录当成零发。已有炮弹可能破坏铁路或目标时，明确说明相关条件无法保证。

本轮不建立一套能推断全部铁路、车站和关卡因果关系的规则库。严格列车计划通过专注期间停止其他自动打击来保护前提；玩家可看见既有在飞事件，对未知外部干扰不宣称绝对控制。

专注计划**成功完成**以后，只有执行开关仍为运行、玩家没有在期间修改控制选择，才解除这次临时暂停并恢复先前队列。专注计划失败、被玩家取消或出现结果不明时，默认保持暂缓，给出继续其他任务的入口。不能刚取消列车方案，系统就转头把车站打掉。

同时只允许一项专注计划占用这个窗口。第二项可以排队；替换当前专注计划必须显式执行取消或改派。超时不自动转交授权。

### 7.5 计划状态与反馈

计划主状态使用有限的流程：草稿、已排队、正在准备、等待条件、等待结果、完成、失败、已取消。暂缓是附加的执行控制状态，机构恢复是炮位状态，避免把每一种组合都扩成新的主状态。

典型过程为：

```text
草稿 → 已排队 → 正在准备 → 等待条件 → 实际发射 → 等待结果
                       ↑                               │
                       └──────── 下一阶段 ───────────────┘
                                                       └→ 完成／失败
任意未终止计划 → 玩家取消 → 已取消（在飞结果仍可继续记入）
```

“等待条件”必须有具体原因，例如另一管尚未准备、目标刚刚转移、尚未确认催泪效果、整列超出覆盖、当前无法解除另一管武装。预定时间到了但没有结果，应显示结果未确认，不把等待包装成完成。

结果区分“发射按要求执行了”与“毁伤／任务目标已确认达成”。每个模板声明自己的完成条件：普通单发可在真实出膛及机构交接后完成执行，毁伤结果另记；要求整列摧毁或前置效果的计划，不能只凭出膛判定全部成功。

未取得确认时，发射记录标为结果未确认，对依赖它的后续阶段保持等待。超过该阶段经校准的观察期限后，转为需要玩家处理的等待，给出继续观察、改派或取消的入口；释放不必持有的共享机构资源，不无限重试或暗中补射。最终显示的成功必须说明达成的是执行要求还是实际毁伤。

正常交互至少能看到：目标与编组成员、方案、计划顺序、当前阶段和等待原因、两管实际装填摘要、已实际发射数量、结果置信情况、可执行操作。内部锁名、代次、回调异常和每帧解算量只留在诊断中，不能成为玩家理解界面的前提。

### 7.6 模板一：一发 HE 拦截整列移动列车

该模板固定表达：**所选固定编组、HE、一发上限、命中时仍满足移动拦截条件、覆盖全部选中成员、专注执行**。首发作为明确条件显示；从开局选择这个方案时可以要求本场景首发，已经开炮后不假装仍能满足。

方案生成与执行依次为：

1. 识别并确认整列成员。展示成员数与可用的运动观测，不能只显示一个匿名红点。
2. 在统一命中时刻外推各成员位置，验证共同运动模型。模型不一致时分别预测或等待更可靠观测。
3. 对完整成员集合计算覆盖圆，使用经验证的有效毁伤范围和必要余量判断可行性。
4. 展示全部覆盖／部分覆盖及预计拦截点。若 HE 只能覆盖部分成员，该草稿不满足本模板；玩家可以明确换方案，系统不能自动改成 HCHE 或多发。
5. 建立专注窗口，确认首发条件和当前在飞情况，然后选择炮管、装药并准备。
6. 发射前检查目标是否仍移动、编组是否完整、解算是否有效。整体匀速平移只更新提前点，不反复搜索最大子集。
7. 发射一发后等待结果；记录实际成员毁伤，不因有幸存者就暗中补射。

当前 `ClusterSolver` 的最大覆盖子集和 `MaxCandidates = 8` 是性能取舍，不能成为“整列”的定义。显式编组超过上限时，需要完整集合的覆盖验证或明确报告暂不支持，不能静默截断。

圆形覆盖成立也不等于必然摧毁全部车厢。伤害、遮挡、成员抗性和目标真正的命中位置要实测。现有友军禁区检查和弹药免疫检查继续参与可行性判断，不能在增加显式编组时丢失。界面可以承诺方案按整列计算，只有毁伤观测充分时才报告整列摧毁。

若准备过程中铁路被其他行为破坏、列车已经停车、成员分离或观测失效，进入等待／需要改派。继续打静止列车是一项可以接受的新命令，但不能被记作成功完成原来的移动拦截要求。

### 7.7 模板二：催泪后接杀伤

该模板绑定同一目标或明确编组，第一阶段使用 TEAR，第二阶段使用玩家指定的杀伤弹。默认专注执行，防止其他自动计划抢先打出杀伤弹。

第二阶段可以提前采购和装填，但在第一阶段门槛成立前必须保持不可自动击发。尤其要防止全局扳机在发射 TEAR 时，把另一管预装的杀伤弹一起打出去。

阶段门槛依该关实际规则确定：可能是催泪弹实际落地、效果命中指定对象，或任务目标发生了相应状态变化。必须先实测关卡到底认哪一个，再绑定最直接、可靠的信号。**TEAR 已提交击发、已出膛、预计飞行时间结束，均不能自行替代“催泪要求已满足”。**

若暂时无法自动观测该信号，提供明确的“我已确认催泪阶段完成，继续”操作，并将它记录为玩家确认。此时仍由玩家掌握顺序；不使用一个固定延时假装自动识别成功，也不把这类玩家确认记作游戏事件证据。

恢复暂停时检查已经实际完成的阶段，避免重发 TEAR。取消计划则取消所有未执行阶段；更换第二阶段弹种不会撤回已发射的第一发。

本轮无需自动读懂电报内容。玩家读完电报以后选择模板，系统保证执行顺序。默认指挥模式通过不擅自开火保留这个机会；玩家主动开启全自动扫荡以后，无法保证所有尚未到来的电报目标都完好。自动扫荡范围与手动排除应可见，但不承诺预测未来剧情。

### 7.8 模板三：两轮双炮 AP 集中攻击

该模板绑定敌方铁巢，计划上限为四发 AP，分两轮、每轮两管组成一个明确齐射组，默认专注执行。按玩家描述以四发 AP 为预期方案；实际击毁规则和容错范围仍需验证。

第一轮两管都准备完成、使用可协调的弹道、绑定同一解算与目标代次，才一起武装并提交全局击发。记录两管真实出膛，不能把一次扳机请求直接计为两发成功。

敌方受击会转移，因此第二轮可以提前装填，却不能提前锁死第一轮的坐标。第一轮结果与目标状态需要重新确认；一旦检测到转移，使第二轮旧解算失效，取得新位置和有效运动模型以后再发射。

这不是要求无条件等敌方停下来：若转移中的运动模型和提前量已验证可用，可继续打移动目标；本轮至少要具备等待稳定后可靠重算的路径。未知位置时不得为了维持“齐射节奏”发出两发旧坐标炮弹。

同一轮的两发是否能在转移影响前命中，要验证实际发射间隔、飞行时间差及敌方受击触发机制。若第一发命中立即改变第二发的命中前提，就报告现有齐射不能保证双中，不能仅凭发射动画同步宣称实现了四发必杀。

目标在两轮之间由本计划持续占用，自动扫荡不能插入攻击观测员或为同目标生成重复计划。已有登记系统需要允许同一计划有意安排的第二轮，并阻止其他来源的重复派发；编组登记和释放应覆盖全部成员。

目标提前击毁时结束剩余阶段并保留装填；四发打完仍存活或结果未知时给出真实结果，不自动无限追加 AP。缺弹、单管故障和中途取消都走统一交接逻辑。

### 7.9 地图作为有时间戳的标绘

地图提供的是一张可以下令的作业图：某时刻的已知位置、方向与速度资料、目标编号或编组范围，以及某项计划的预计拦截点与覆盖范围。过去位置和计划落点必须能被区分，不能都画成“敌人现在就在这里”。

显示标记固定在本次标绘的坐标，选择绑定则一直指向目标身份。后台继续计算提前量；显示标记不跟着每次求值移动，玩家也不必为了跟踪目标不断重新点选。

采用以下更新规则：

| 事件 | 标绘与反馈 |
|---|---|
| 首次发现目标或收到一条可识别的新情报 | 加入带观测时刻的标绘，注明来源 |
| 玩家选择“重新标绘” | 使用当前可用数据重画，保留采样时间与标绘时间的区别 |
| 玩家选择目标、修改或提交方案 | 显示该次方案的预计拦截和覆盖，注明它属于哪项计划 |
| 已确认停车、重新启动、转向、紧急转移或成员变化 | 使旧预测失效，更新相关标绘或标记需要重新确认 |
| 实际发射 | 记录已发射，可一次性盖上最终发射方案的预计落点 |
| 结果被确认 | 更新毁伤、完成或失败状态；未知结果保留未知 |
| 常规后台扫描与提前点计算 | 更新内部观测与解算，不自动重画所有目标 |

识别运动变化采用有证据的阈值或稳定判定，避免微小噪声制造连续“重大变化”。等待导致原方案预测过时时，保留它作为有日期的旧方案或标记需要更新，不能继续声称它是实时落点。

默认关闭逐秒落点倒计时、连续飞行进度条和跟随预测位置移动的目标图标。以“准备中、已发射、等待结果、结果已确认”等离散状态回应玩家。需要排查弹道和 CBT 的开发诊断可以保留精确 ETA、误差和发射日志，不作为正常控制台中心内容。

原作已经提供的 CBT 时钟可以继续作为机制信息使用；隐藏炮弹 ETA 不等于隐藏玩家需要决策的原有倒计时。减少界面刷新也不等于降低后台解算精度。

### 7.10 情报来源的边界

当前读取 `FireMission.Entities` 能得到玩家未必拥有的目标信息。静态标绘只改变表达方式，不能消除这个信息优势，也不能把直接读取的坐标包装成电报推算。

目标观测保留来源、采样时刻和有效性。当前可以继续使用任务实体数据，后续再增加电报、观测员或玩家手工标绘的来源适配；计划层不应依赖某个 Unity 根对象路径。不同来源精度不足时，允许显示不确定或要求确认。

本轮不强求完成信息公平化。这样既保留 FCS 的自动开炮定位，也给更受限的玩法留下接口，不为这三个收尾问题引入另一场整体重构。

### 7.11 三维控制台留到下一阶段决定的部分

控制台以后可以用地图铅笔、编号标牌、计划条、机械选择器、状态灯和原作风格的按钮表达上述动作。但按钮、拨杆、旋钮、摇杆各几个、摆在哪里、用什么模型，以及用鼠标还是游戏中的画图笔点选，都没有在本文中定死。

无论采用哪种前端，都调用同一套命令，展示同一份状态。先用临时面板或现有按键入口验证完整流程，不能在临时版里把“取消”做成清队列，等三维模型做好才补真正的取消。

小键盘可以保留为快捷键或诊断入口；最终正常操作不要求玩家背快捷键。控制台的参与感主要来自选择对象、表达方案、观察执行与改变决定，实体按钮用于承载这些明确动作。

依据：[聚群历史设计](../cluster-strike.md)、[ClusterSolver](../../IronNestFCS.Logic/FCS/ClusterSolver.cs)、[旧地图 Overlay 设计](../superpowers/specs/2026-08-13-map-overlay-visual-design.md)。旧 Overlay 中实时标记与倒计时的取舍，以本文新的标绘原则为准。

## 8. 实现边界与落地顺序

### 8.1 在现有执行器上分清职责

保留已经有效的射表、匀速外推、聚群几何工具和机械操作能力。新增的计划层先支持有限模板，不从机器学习项目或历史 CBT 分支搬来一整套新系统。

数据与命令按以下方向流动：

```text
游戏观测 → 有来源和时间的目标／实物状态 → 草稿与计划 → 单发执行
                    ↑                                  │
                    └──── 实际机构、出膛、命中与计时器事件 ──┘

玩家命令 → 计划授权与执行控制
自动策略 → 同一套计划入口
地图／控制台 ← 同一份选择、计划与结果状态
```

任务生成者负责提出要做什么，执行器负责判断现在能否做、操作机构并返回实际结果。两者都不能单独宣布“这一发已经命中”。显示层也不能通过倒计时归零来推动任务状态。

| 现有位置 | 本轮需要承担或调整的职责 |
|---|---|
| `FcsModule`、`TacticalDecider` | 分开观测、计划生成与执行授权；普通策略和 CBT 提交统一计划 |
| 新增的有限计划逻辑 | 保存固定目标、阶段、硬性要求、修订、暂停与结果；不直接点击游戏机构 |
| `FSC`、`ArtilleryTask` | 执行一个有效阶段中的单发或齐射；取消与交接统一；所有回调检查所属身份 |
| `GunSystem`、`TriggerConsole` | 提供有未知值的实物读数，以及能验证结果的装填、解除武装和击发操作 |
| `CoroutineLock`、采购与炮塔操作 | 按持有者释放资源，登记子动作，避免共享资源相互等待 |
| `TacticalRadar`、`TargetLeadSolver`、`MapTable` | 统一坐标与时间含义，保留采样时刻，处理目标和本舰运动变化 |
| `ClusterSolver`、`TargetRegistry` | 区分全编组验证与最大子集优化；管理跨阶段和全成员占用 |
| 发射记录与 CBT 观测 | 独立于任务槽位和界面记录真实出膛、预测、结果及计时器变化 |
| `MapOverlay`、`FcsWindow`、后续三维控制台 | 只提交命令与展示状态；复用同一语义，不各写一份调度 |

这些是职责划分，不要求一项对应一个新框架或服务。能通过少量明确数据结构和现有协程完成的，就不要为了形式扩大工程。

### 8.2 分阶段交付

| 阶段 | 可交付内容 | 进入下一阶段的条件 |
|---|---|---|
| P0：验证关键原作机制 | 最小诊断记录、可重复场景；确认解除武装、实际装药、出膛、CBT 和移动坐标来源 | 明确哪些字段可用，哪些承诺只能等待确认；不要求先理解整套游戏 |
| P1：执行可靠性 | 实物状态、占用身份、取消与接管、统一命令入口、最小计划契约及临时状态显示 | 每个装填阶段都能暂停／取消／恢复，双炮不会被误带响，旧任务不会清理新任务 |
| P2：CBT 与移动 | 独立发射记录、FDC 落地顺序、倒计时状态、统一移动恢复、有限资源策略 | 时序不成立时明确降级；移动和中断以后可恢复；Baseline 回归通过 |
| P3：玩家计划可用 | 单发、整列 HE、TEAR 后杀伤、两轮 AP；优先与专注；临时面板及事件标绘 | 三个关卡场景的逻辑闭环能够通过实际操作完成 |
| P4：三维控制台 | 按已验证流程设计实体交互、模型、反馈和快捷操作 | 不依赖背小键盘完成主要流程；实体操作保持同一套命令语义 |

P1 就实现第三方向需要的授权、暂停、选择与提交契约；P3 补全具体方案和可操作流程。这样前两项不会再次绑死在旧小键盘开关上，三维美术也不成为修复取消的前置条件。

每阶段完成后保持一个可用的 Baseline 版本，CBT 可选。旧分支里已经失败的策略只取可验证的部分，不一次性重新启用。当前工作区已有的射表修改和相关检查保持独立，不在文档或调度重构中顺手覆盖。

P3 达成后即可认为核心逻辑收尾；P4 是完成控制台体验的最后一项。此后是否继续做受限情报、行进间射击或学习型智能体，是新项目选择，不反过来推翻这次完成标准。

## 9. 验收场景

以下是未来实现的验收要求，**不是本次已经通过的测试结果**。每项记录游戏版本、关卡、时间倍率、资源与弹药条件、操作时刻、真实机构状态和实际发射／效果事件。失败时能知道卡在哪一步，比日志最后一句写“完成”更有价值。

### 9.1 取消、接管与状态恢复

| 编号 | 场景与操作 | 验收结果 |
|---|---|---|
| C01 | 在选弹、推弹头、选药、推药、合栓、武装、待击发各阶段分别暂缓与取消 | 后续可撤销动作停止；实物被保留或交接；恢复不重复推药、不自动强发 |
| C02 | 左炮已武装后取消，随后让右炮执行单发 | 确认左炮解除武装才允许自动扳机；无法确认则等待，不带响左炮 |
| C03 | 击发请求提交与出膛事件之间取消 | 显示击发待确认；实际出膛则保留记录；不错误重发或宣称撤回 |
| C04 | 膛内留下同弹种兼容装药，再下新计划；随后测试不同弹种或不可达装药 | 兼容时复用，不兼容时换炮或等退弹；不暗中丢弹、换弹或套用未验证弹道 |
| C05 | 让旧任务取消后的回调晚于新任务占用到达 | 旧任务不能清空新槽位、释放新锁、触发下一发或改写新结果 |
| C06 | 在阶段等待中制造观测失败、超时或异常 | 不把未知当空膛、超时当成功；进入有原因的恢复；重复请求不会重复采购／复位 |
| C07 | 玩家修改装填、武装或炮塔；再选择继续 | 系统停止争抢操作，按实际状态重新校验；手动武装的另一管不会被自动带响 |
| C08 | 一管故障，另一管可用；分别测试能否确认武装隔离 | 可隔离时允许另一管工作；存在全局误击发风险时暂缓自动击发 |
| C09 | 暂停、取消、切换模式后继续扫描目标 | 暂停目标仍保留；明确取消的目标不被扫荡立刻捡回；模式切换不复活旧计划 |
| C10 | 装填中或已有在飞炮弹时热重载 | 旧动作停止，新逻辑暂缓并读取实物；在飞信息保留或明确未知，不直接重开火 |

暂停等待本身不是死锁，不应被看门狗误判为需要强发。测试必须区分“有明确等待原因”“操作失败正在恢复”和“没有进展也没有可解释原因”。

### 9.2 CBT、落地顺序与紧急移动

| 编号 | 场景与操作 | 验收结果 |
|---|---|---|
| B01 | 一发远距离长飞行炮弹在飞，准备近距离 FDC 射击 | FDC 按预计时间范围排在相关旧炮弹之后；无法保证则改排程，不仅按发射先后排序 |
| B02 | 两管指向不同方位，短飞行任务等待另一管先执行 | 不持有对方必需的炮塔造成互等；重获资源后再次验证解算与武装 |
| B03 | FDC 发射后未击毁、未暂停，或有迟到／手动炮弹解除暂停 | 以实际 CBT 状态调整，不停在预期状态；未知在飞情况可见 |
| B04 | 暂停期间长时间停火，观察是否自行恢复；改变游戏暂停与倍率 | 不把游戏暂停当 FDC 成功，不写死无限暂停，不混用真实秒与游戏秒 |
| B05 | 装填、瞄准、已武装和待齐射时分别触发紧急移动 | 统一交接并禁止旧许可开火；位置有效以后按保留弹药与目标重算 |
| B06 | 沿目标径向移动，目标方位几乎不变；再测试横向移动 | 距离、装药可达性、仰角和飞行时间均更新，不仅检查角度变化 |
| B07 | 指挥模式中手动移动，或移动时暂停／取消 | 同样触发位置失效和恢复；移动结束不恢复已撤销的授权 |
| B08 | 连续请求移动、购买响应迟到、位置引用暂失 | 同一次请求不重复花费；未知位置不记为零或已稳定；有明确恢复状态 |
| B09 | 我方移动前已有炮弹出膛 | 原发射位置和预计事件保留；仅未发射解算按新位置重算 |
| B10 | 剩余时间紧、资源不足、无可用 FDC，或关闭自动移动 | 策略报告真实限制，不换掉手动计划弹种，不凭空重置倒计时，不无限等待成功 |

| I10 | 等待炮弹飞行，预计时间到但没有确切效果证据 | 默认不逐秒倒计时，也不自动显示命中；离散反馈准确保留未知 |
| I11 | 自动扫荡时明确取消目标，之后模式切换，再出现复用 ID 的新单位 | 原目标遵守排除，新实例不错误继承旧占用；无法辨别实例时明确提示 |

### 9.4 如何验证以及何时停止扩张

对可脱离游戏的权限、所有权、阶段转换、事件顺序和坐标计算做少量有意义的回归检查。重点覆盖旧回调释放新资源、乱序事件、暂停后恢复、同方位距离变化等实际失败模式，不为每个字段写一份镜像测试。

机构动画、全局扳机、原作计时器和任务目标通过实机验证。日志至少能够串起计划、阶段、炮管、事件时间与结果来源；正常控制台不必暴露这些诊断字段。

保留既有 Baseline 和移动目标精度回归。CBT 性能比较采用相同游戏版本、场景、倍率与初始资源，记录存活时间、征用点变化、有效命中、无效炮弹和需要手动解卡的次数。随机移动导致的差异单独记录，不用一次漂亮录像替代稳定性证据。

本轮没有“必须超越所有玩家或其他 mod”的指标。三个意图场景能按要求执行，取消与移动不再制造失控状态，失败有原因且能继续接管，就是可完成、可发布的结果。

## 10. 待验证机制与后续外观问题

### 10.1 开工前后按需确认的游戏机制

这些不确定项决定实现选用哪个观测信号，或某个方案能提供多强的保证。它们不改变玩家命令的基本语义。

| 问题 | 验证方式 | 在确认之前的行为 |
|---|---|---|
| 怎样读取真实装药、合栓、机构运动与武装状态？ | 对照分阶段实物操作、字段、事件和动画 | 保留未知值，不提前复用或自动击发 |
| 解除武装是否能阻止另一管全局扳机带响？ | 双炮准备后单管撤销，实测继电器和实际出膛 | 未确认隔离则暂缓自动全局击发 |
| 扳机请求何时不可撤销，哪些事件可靠代表出膛和落地？ | 记录请求、机构、炮弹与事件的相对时序 | 使用击发待确认／结果未知，不伪造成功 |
| FDC、后续落地与移动分别如何改变 CBT？暂停会否自行结束？ | 复现旧例，直接观测专用计时器及事件 | 响应实际状态；不保证永久暂停 |
| 当前版倒计时奖励、移动价格和资源限制是否与历史一致？ | 隔离操作前后读取计时器和征用点 | 读取或校准参数，不把历史数字当规则 |
| 地图在移动、缩放、关卡变化后是否重置原点或旋转？ | 比较本舰、固定地物、目标及面板坐标 | 无可靠变换时暂停发射，不能用零值代替 |
| 列车的成员关联、有效毁伤范围和 HE 一发毁伤是否满足预期？ | 完整成员名单、覆盖计算与命中后状态对照 | 可以提供整列计算，不保证未经验证的全毁 |
| 支援关卡认可 TEAR 的哪个事件？ | 单独完成任务阶段并观察目标／任务状态 | 玩家明确确认阶段完成，保留确认来源 |
| 敌方铁巢的 AP 毁伤和转移触发时机？齐射有多大容许间隔？ | 分别记录两管出膛、命中、敌方位移与血量／存活 | 不宣称同步动画等于双中，不承诺四发必杀 |
| 目标停车后再启动、场景卸载及 ID 复用如何识别？ | 对照连续实例观测与场景生命周期 | 身份或运动不可信时暂停绑定计划 |
| 实际 ToF 误差如何随弹种、装药、距离变化？ | 复用射表数据并补必要实测 | 严格顺序不使用未经校准的狭窄时间窗口 |

个别机制无法完整自动观测时，应收窄功能承诺或保留明确的人工确认入口。不能以“先假设成立”把未知藏回状态机，也不需要为了这份有限设计逆向整个游戏。

### 10.2 后续再商量的控制台外观

后续设计要解决的是：实体控件怎样排列；选目标、选方案和执行状态怎样分区；如何在地图和计划条之间切换；哪些反馈适合仪表、指示灯、文字或声音；原作鼠标与画图笔的射线交互如何接入。

可以先用三个场景做纸面或临时界面演练，再决定具体旋钮和按钮数量。不能先摆一桌漂亮开关，再反过来替每个开关寻找功能。

本轮已经确定而不应再悬置的部分包括：选中不等于开火、提交才授权、优先不等于专注、暂停不等于取消、取消不等于退弹、编组不等于任意覆盖子集、预计落地不等于效果确认、地图标记不等于实时真值。

## 11. 完成标准与资料索引

### 11.1 本轮设计决定

| 决定 | 对实现的约束 |
|---|---|
| 保留全自动脚本的定位，同时增加玩家指挥 | 两种方式共用执行器；玩家可以只决定对象和方案 |
| 先修执行、再修 CBT、最后做三维外观 | 交互契约提前落地，外观不阻塞逻辑验证 |
| 取消按真实物理状态交接 | 不再用强发、清队列或无条件清膛代替取消 |
| 一项计划拥有目标、阶段和发射结果 | 单发结束不等于整项计划结束 |
| 实际事件驱动关键顺序 | 出膛、预计落地、实际效果分别记录 |
| 保留解析外推与后台精度 | 不为制造复古视觉而故意降低命中计算质量 |
| 地图采用静态、有时间戳、按事件更新的标绘 | 默认关闭逐秒炮弹倒计时和实时移动目标大屏 |
| 三个具体意图模板足够作为本轮范围 | 不扩张为通用任务理解、无限优化或机器学习重构 |
| 对全知数据来源保持明确 | 预留来源边界，信息公平化另开议题 |

逻辑完成的标志是：玩家可以可靠地改变决定；CBT 能利用已验证的机制并应对失效；三个关卡例子能从选择、下令一直走到真实结果或明确失败。三维控制台完成的标志是：玩家能自然地操作这些已有能力，而不必依赖小键盘记忆。

这些标准达成以后，FCS 可以作为一款范围明确的自动火控 mod 收尾。进一步追求行进间射击、更严格情报限制或学习型智能体，需要新的目标和独立验收，不属于“这版还不算做完”。
